# What is Idempotency in API & System Design?

In distributed systems and RESTful APIs, network glitches, timeouts, or client retries can cause the exact same request to be sent multiple times. Without proper safeguards, duplicate requests can lead to duplicate payments, corrupted database records, or unintended state changes.

This is where **Idempotency** comes in. In this article, you can find what idempotency is, why it is critical for reliable software architecture, how HTTP methods handle it, and how to implement an **Idempotency Key** mechanism.

---

## What is Idempotency?

An operation is considered **idempotent** if performing it once produces the exact same system state and outcome as performing it multiple times with the same input.


```

Initial State: Account Balance = $100

Non-Idempotent (Subtract $10 three times):
Request 1 => Balance = $90
Request 2 => Balance = $80
Request 3 => Balance = $70  <-- System state changed unexpectedly

Idempotent (Set Balance to $90 three times):
Request 1 => Balance = $90
Request 2 => Balance = $90
Request 3 => Balance = $90  <-- System state remains consistent

```

In math: $f(x) = f(f(x))$

---

## Idempotency in HTTP Methods

The HTTP specification defines standard semantics for request methods based on safety and idempotency:

| HTTP Method | Safe? | Idempotent? | Description |
| :--- | :--- | :--- | :--- |
| **GET** | Yes | **Yes** | Retrieves data without modifying server state. |
| **HEAD / OPTIONS**| Yes | **Yes** | Fetches headers/metadata without side effects. |
| **PUT** | No | **Yes** | Replaces a target resource entirely. Updating with the same payload repeatedly yields the same state. |
| **DELETE** | No | **Yes** | Removes a resource. Deleting an ID once or 10 times leaves the resource gone (returns 404 on retries, but server state remains unchanged). |
| **POST** | No | **No** | Creates new resources or triggers actions. Executing POST twice creates two distinct records. |

> **Note:** Even though `POST` is non-idempotent by default, we can make `POST` endpoints idempotent (such as payment checkouts) using **Idempotency Keys**.

## How to Implement Idempotency: The Idempotency Key Pattern

To safely handle retries on non-idempotent operations (like `POST /v1/payments`), APIs use a unique header token called an **Idempotency Key** (usually a UUID generated by the client).


```

[ Client ]                                     [ API Gateway / Server ]              [ Cache / Redis ]
|                                                     |                                  |
| --- 1. POST /payments (Header: Idempotency-Key: X) -> |                                  |
|                                                     | --- 2. Check Key "X" in Cache -> |
|                                                     | <--- 3. Key Not Found ---------- |
|                                                     |                                  |
|                                                     | === 4. Process Payment ===       |
|                                                     |                                  |
|                                                     | --- 5. Save Key "X" + Response ->|
| <--- 6. Return 200 OK (Payment Success) ----------- |                                  |
|                                                     |                                  |
[Network Retry]                                              |                                  |
|                                                     |                                  |
| --- 7. POST /payments (Header: Idempotency-Key: X) -> |                                  |
|                                                     | --- 8. Check Key "X" in Cache -> |
|                                                     | <--- 9. Key Found (Cached Result) |
| <--- 10. Return Cached 200 OK (No re-processing) -- |                                  |

```

### Step-by-Step Flow

1. **Client Request:** The client generates a unique key (e.g., `Idempotency-Key: 9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d`) and sends it in the request header.
2. **Server Check:** The API layer checks a distributed key-value store (like Redis) to see if this key has been processed before.
3. **First Processing:** If the key is **new**:
   - The server locks the key to prevent concurrent race conditions.
   - It executes the underlying business logic (e.g., charging a credit card).
   - It stores both the **status** and the **response payload** in Redis tied to that key, usually with a Time-To-Live (TTL, e.g., 24 hours).
   - It returns the HTTP response to the client.
4. **Duplicate Request Handling:** If the key **already exists**:
   - The server bypasses the business logic completely.
   - It directly returns the saved, cached response payload back to the client.

---

## Key Considerations & Challenges

1. **Locking & Race Conditions:** If two identical requests with the same key arrive at the exact same millisecond, the system must use atomic locks (e.g., Redis `SETNX`) so only one request enters the execution pipeline while the other waits or receives a `409 Conflict` status.
2. **Key Expiration (TTL):** Idempotency keys should not stay in RAM forever. A expiration window of 24 to 72 hours is standard for payment and order systems.
3. **Payload Mismatch Validation:** If a client reuses an existing `Idempotency-Key` but changes the request body (e.g., changing amount from $10 to $100), the server should reject the request with a `422 Unprocessable Entity` or `400 Bad Request` error.

---

## Summary

Designing APIs for real-world network instability requires handling retries gracefully:

- **Idempotency** guarantees that duplicate requests cause no extra side effects.
- Methods like **GET**, **PUT**, and **DELETE** are naturally idempotent.
- **POST** operations (such as financial transactions or booking operations) should be protected using an **Idempotency-Key** pattern with a fast key-value store like Redis.
